## 1. Цель и границы

HomeCloud Device Bridge — отдельный Go-процесс на том же узле, что и HomeCloud Backend. Он обнаруживает физические устройства, поддерживает их протокольные подключения, преобразует абстрактные команды HomeCloud в операции конкретного драйвера и нормализует поступающие от устройств данные.

Главный архитектурный принцип:

**Backend управляет логической моделью HomeCloud и принимает решения о допустимости операций. Bridge знает физический способ взаимодействия с устройством и выполняет маршрутизацию к нужному драйверу. UI взаимодействует только с Backend.**

### 1.1. Backend отвечает за

- постоянную идентичность и реестр физических устройств;
- каталог типов устройств и стандартных возможностей HomeCloud;
- фактический набор возможностей каждого устройства;
- текущее состояние устройств и хранение истории телеметрии;
- проверку существования устройства, поддержки команды и пользовательских разрешений;
- публичный API и WebSocket-контракт для UI;
- маршрутизацию абстрактной команды в Bridge;
- управление процессом Bridge и его общим состоянием.

### 1.2. Device Bridge отвечает за

- обнаружение устройств через локальные интеграции;
- протокольные подключения и их жизненный цикл;
- встроенные Go-драйверы;
- runtime-карту активных устройств, драйверов и обработчиков;
- преобразование абстрактных команд в протокольные операции;
- приём ответов и телеметрии, нормализацию и передачу в Backend;
- локальную проверку того, что команда может быть обработана текущим драйвером;
- восстановление соединений с физическими устройствами.

### 1.3. UI отвечает за

- получение модели устройств и доступных возможностей от Backend;
- отображение элементов управления на основании стандартных Capability;
- отправку команд Backend;
- отображение состояния, ошибок и результатов исполнения.

UI не подключается к Bridge и не знает о драйверах, протоколах, адресах устройств или внутренних идентификаторах протокола.

### 1.4. Вне области v1

- динамически загружаемые бинарные плагины;
- отдельная БД Bridge;
- прямое взаимодействие UI ↔ Bridge;
- обязательные облака производителей;
- универсальный движок автоматизаций;
- хранение полной истории телеметрии в памяти Backend;
- удалённое подключение Bridge с другого узла. В v1 Backend и Bridge находятся на одном хосте.

## 2. Общая схема

    Физические устройства
            ↕ протоколы
    Драйверы Device Bridge
            ↕
    Device Bridge Runtime
            ↕ локальный IPC
    HomeCloud Backend
       ├── Device Type Registry
       ├── Capability Registry
       ├── Device Registry
       ├── Device State Registry
       ├── Command Validation / Authorization
       └── Existing WebSocket + Event Bus
            ↕ WebSocket v1
          HomeCloud UI

Потоки данных:

1. Обнаружение: устройство → драйвер → Bridge → IPC → Backend → реестры → событие UI.
2. Команда: UI → Backend WS → проверка возможностей и прав → IPC → Bridge Router → драйвер → устройство.
3. Результат: устройство/драйвер → Bridge → IPC → Backend → состояние/событие UI.
4. Телеметрия: устройство → драйвер → Bridge → IPC → Backend → текущее состояние и, при необходимости, история.

## 3. Контракт Backend ↔ UI

Backend сохраняет существующий публичный протокол WebSocket JSON v1. Новое подключение UI или новый публичный порт для Device Bridge не требуются.

Существующий конверт сообщения Backend использует поля v, id, type, action и data. Новые команды устройств регистрируются через существующий commands.Registry, а события публикуются через существующий events.Bus.

### 3.1. Получение устройств

UI получает список устройств и их UI-модель через команду Backend. Модель должна содержать:

- стабильный device_id;
- функциональный device_type;
- отображаемые метаданные: имя, производитель, модель;
- фактические capabilities;
- сущности и их схемы;
- текущее состояние и время обновления;
- доступные для текущего пользователя действия.

Состав доступных действий вычисляет Backend. Он учитывает одновременно фактические возможности устройства и разрешения пользователя.

### 3.2. Отображение UI

Capability — стандартная функция HomeCloud, а не имя протокольной команды.

Backend предоставляет UI идентификаторы и схемы известных возможностей. UI сопоставляет их со своими штатными компонентами. Например:

| Capability | Возможное представление |
|---|---|
| switch | переключатель питания |
| brightness | ползунок яркости |
| color | выбор цвета |
| color_temperature | настройка цветовой температуры |
| power_monitoring | показатели мощности, напряжения и тока |
| temperature | значение температуры |
| humidity | значение влажности |

Bridge не передаёт произвольный HTML, React-компоненты или инструкции на исполнение UI-кода.

Неизвестная UI возможность не должна ломать экран: UI может показать базовые метаданные устройства и пропустить неподдерживаемый виджет.

### 3.3. Команда UI

Пример запроса на изменение яркости:

    {
      "v": 1,
      "id": "ui-request-001",
      "type": "command",
      "action": "devices.command",
      "data": {
        "device_id": "light-001",
        "capability_id": "brightness",
        "command_id": "set",
        "parameters": {
          "value": 75
        }
      }
    }

Backend проверяет:
1. Существует ли устройство.
2. Зарегистрирована ли у устройства capability brightness.
3. Известна ли команда set в каталоге этой capability.
4. Соответствуют ли параметры её схеме.
5. Разрешено ли текущему субъекту выполнять эту операцию.
6. Доступен ли Bridge.

Если capability отсутствует, Backend отклоняет запрос и не передаёт его Bridge. Например, команда brightness не может быть отправлена розетке, у которой такой возможности нет.

UI не может самостоятельно объявить устройству новую возможность или обойти проверку Backend.

### 3.4. Возможности и разрешения — не одно и то же

- Capability означает, что физическое устройство технически умеет выполнять операцию.
- Permission означает, что текущему пользователю разрешено её выполнять.
- UI получает только итоговый набор доступных действий.

Таким образом, наличие capability не даёт автоматически право управлять устройством.

## 4. Реестры Backend

Все постоянные реестры принадлежат Backend и хранятся в его SQLite. Bridge не создаёт параллельный постоянный каталог устройств.

### 4.1. Device Type Registry

Каталог функциональных типов HomeCloud: light, smart_plug, temperature_sensor, motion_sensor и другие.

Тип описывает назначение устройства и общую категорию отображения. Он не является доказательством наличия конкретной возможности.

Две розетки типа smart_plug могут иметь разные capabilities. Производитель, модель, аппаратная ревизия и версия прошивки — метаданные конкретного устройства, а не функциональный тип.

### 4.2. Capability Registry

Канонический каталог возможностей HomeCloud. Для каждой capability Backend определяет:

- стабильный идентификатор и версию схемы;
- доступные команды;
- схемы и ограничения параметров команд;
- сущности состояния;
- типы значений и единицы измерения;
- метаданные представления для UI;
- при необходимости — семантику разрешений.

Каталог является системным контрактом HomeCloud. Bridge сообщает, какие capabilities поддерживает устройство, но не может произвольно менять глобальные схемы команд или UI.

### 4.3. Device Registry

Содержит конкретные физические устройства:

- device_id;
- функциональный тип;
- имя пользователя;
- производитель, модель, аппаратная ревизия, прошивка;
- источник обнаружения в виде непрозрачной метки Bridge;
- список фактически поддерживаемых capabilities;
- состояние регистрации и доступности;
- даты обнаружения и последнего контакта.

Backend — единственный владелец постоянной записи устройства.

### 4.4. Device State Registry

Содержит последнее известное состояние сущностей устройства. Значение состояния отделено от описания возможности.

Например, лампа может поддерживать brightness, но значение яркости пока неизвестно. Это не означает, что capability отсутствует.

Каждое обновление состояния должно иметь:
- device_id и entity_id;
- типизированное значение;
- время измерения/получения;
- признак качества или доступности, если применимо;
- источник/версию обновления для защиты от устаревших данных.

### 4.5. История телеметрии

Текущее состояние и история — разные задачи. Device State Registry хранит последнее известное значение. История телеметрии может сохраняться отдельным механизмом Backend с политикой хранения и ограничением объёма.

Bridge передаёт измерения, но не определяет политику долговременного хранения.

### 4.6. Системные и динамические данные

Системные определения Device Types и Capabilities поставляются с Backend и версионируются вместе с ним. Фактические устройства, связи device → capabilities и их состояния динамические и хранятся в SQLite.

Пользовательские расширения каталога не входят в обязательный объём v1. Неизвестная capability не должна молча приниматься как известная команда.

## 5. Контракт регистрации устройства

Bridge передаёт Backend декларацию обнаруженного устройства. Декларация описывает функциональный тип, метаданные и фактические capabilities, но не содержит протокольных инструкций для UI.

Концептуальный пример:

    {
      "device_id": "light-001",
      "device_type": "light",
      "metadata": {
        "manufacturer": "Example",
        "model": "Bulb A",
        "firmware_version": "1.2.0"
      },
      "capabilities": [
        {
          "id": "switch",
          "entities": [
            { "id": "power", "value_type": "boolean" }
          ]
        },
        {
          "id": "brightness",
          "entities": [
            {
              "id": "brightness",
              "value_type": "integer",
              "unit": "%"
            }
          ]
        }
      ]
    }

Это иллюстрация доменной модели, а не окончательная JSON Schema.

Backend выполняет регистрацию:

1. Проверяет формат и размер декларации.
2. Проверяет device_type по Device Type Registry.
3. Проверяет каждую capability по Capability Registry.
4. Проверяет сущности и совместимость с определениями capabilities.
5. Создаёт или обновляет устройство и связи с capabilities.
6. Сохраняет изменения транзакционно.
7. Возвращает Bridge результат регистрации и актуальную ревизию описания.

Если драйвер сообщает неизвестную capability, Backend не должен регистрировать её как исполняемую. Устройство можно поместить в состояние ограниченной/неполной регистрации и записать диагностическое событие. Точное поведение для неизвестного типа требует согласования до реализации.

Повторная декларация обновляет запись, а не создаёт дубликат. Временное исчезновение устройства из сети меняет доступность, но не удаляет запись и последнее известное состояние.

## 6. Маршрутизация команд

### 6.1. Backend

Backend не выбирает протокол или драйвер. Он выполняет логическую проверку и передаёт Bridge абстрактную команду:

    {
      "device_id": "light-001",
      "capability_id": "brightness",
      "command_id": "set",
      "parameters": {
        "value": 75
      },
      "request_id": "backend-request-001",
      "capability_revision": 3
    }

Backend проверяет команду по собственному каталогу и фактическим capabilities устройства до IPC-вызова.

### 6.2. Bridge Router

Bridge получает команду и:

1. Находит runtime-запись устройства по device_id.
2. Определяет активное подключение и экземпляр драйвера.
3. Проверяет, что runtime-декларация поддерживает capability и command.
4. Проверяет параметры по локальной схеме драйвера.
5. Находит обработчик команды.
6. Преобразует параметры в протокольную операцию.
7. Выполняет её через драйвер.
8. Возвращает этап и результат выполнения Backend.

Runtime-карта Bridge — это не второй постоянный Device Registry. Она содержит только текущие подключения, экземпляры драйверов, локальные обработчики и необходимое для исполнения состояние.

### 6.3. Повторная проверка

Backend — первая точка проверки, Bridge — последняя точка проверки перед физическим действием.

Это необходимо, поскольку устройство может отключиться, драйвер может перезапуститься, а набор возможностей может измениться после последней синхронизации.

При несовпадении ревизий или возможностей Bridge возвращает структурированную ошибку, а Backend инициирует обновление декларации устройства.

### 6.4. Статусы команд

Необходимо различать:
- accepted — Bridge принял команду;
- executing — драйвер начал выполнение;
- succeeded — получено достаточное подтверждение успешного выполнения;
- failed — выполнение завершилось ошибкой;
- timeout — подтверждение не получено в установленный срок;
- unavailable — устройство или подключение недоступно.

Факт отправки пакета не равен успешному выполнению физического действия.

Для асинхронных операций Backend возвращает UI идентификатор команды и начальный статус, а окончательный результат публикуется событием. Повторная отправка с тем же command/request ID не должна приводить к повторному физическому действию без проверки идемпотентности.

## 7. Телеметрия и состояние

Драйвер преобразует данные протокола в нормализованные значения HomeCloud. Bridge передаёт Backend device_id, entity_id, значение и временные метки.

Backend:
1. Проверяет, что сущность зарегистрирована у данного устройства.
2. Проверяет тип значения и единицу измерения по каталогу.
3. Отбрасывает некорректные или устаревшие обновления.
4. Обновляет последнее известное состояние.
5. При включённой политике записывает измерение в историю.
6. Публикует событие для подписчиков UI.

Пример нормализованного измерения:

    {
      "device_id": "plug-001",
      "entity_id": "power",
      "value": 125.4,
      "unit": "W",
      "measured_at": "2026-11-23T10:20:30Z"
    }

Bridge не выбирает, сколько дней хранить историю энергопотребления, и не становится источником данных для Monitoring напрямую.

События Event Bus являются механизмом доставки обновлений, а не долговременным хранилищем. После переподключения UI должен иметь возможность получить актуальный snapshot из Backend.

## 8. Backend ↔ Bridge: локальный IPC

### 8.1. Транспорт

Предпочтительный транспорт v1:
- Linux: Unix domain socket;
- Windows: named pipe;
- loopback TCP допускается только как резервный вариант, если платформенная реализация IPC создаёт неприемлемые ограничения.

Backend создаёт и контролирует IPC endpoint. Bridge запускается как дочерний процесс и подключается к endpoint Backend.

IPC не публикуется в LAN или Интернет.

### 8.2. Формат сообщений

IPC имеет собственную версию протокола и не является публичным WebSocket API. Для v1 используется JSON с явным фреймированием сообщений. Предлагаемый формат кадра: 4-байтовая длина в network byte order, затем JSON payload. Максимальный размер кадра должен быть ограничен конфигурацией.

Базовый конверт:

    {
      "protocol_version": 1,
      "message_id": "message-uuid",
      "type": "request",
      "action": "bridge.status",
      "payload": {}
    }

Для ответа используется correlation_id, связывающий ответ с message_id запроса. Для событий применяется отдельный тип сообщения и уникальный event_id.

Все сообщения валидируются по типу, размеру, версии и обязательным полям. Неизвестные обязательные версии и неподдерживаемые типы приводят к контролируемой ошибке, а не к молчаливой интерпретации.

### 8.3. Минимальные группы сообщений

| Направление | Сообщения | Назначение |
|---|---|---|
| Bridge → Backend | hello | Версия протокола и идентичность процесса |
| Backend → Bridge | hello.accepted | Согласование версии и параметров |
| Bridge → Backend | bridge.ready | Runtime готов принимать команды |
| Обе стороны | heartbeat / heartbeat.ack | Контроль живости канала |
| Bridge → Backend | device.discovered / device.updated | Декларация устройства |
| Backend → Bridge | device.registration.result | Результат регистрации |
| Backend → Bridge | device.command | Абстрактная команда |
| Bridge → Backend | command.accepted / command.result | Принятие и результат |
| Bridge → Backend | device.state.changed | Нормализованное состояние |
| Bridge → Backend | device.availability.changed | Доступность устройства |
| Backend → Bridge | bridge.shutdown | Контролируемое завершение |
| Bridge → Backend | bridge.stopping | Подтверждение начала остановки |

Названия и точные JSON Schema должны быть зафиксированы в отдельной спецификации IPC-протокола до реализации. Таблица задаёт обязательный состав взаимодействия v1.

### 8.4. Handshake

Последовательность подключения:

1. Backend создаёт IPC endpoint и запускает Bridge.
2. Bridge подключается к локальному endpoint.
3. Bridge отправляет hello с версией IPC-протокола и версией сборки.
4. Backend проверяет совместимость.
5. Backend отправляет hello.accepted с согласованными параметрами.
6. Bridge восстанавливает runtime драйверов и отправляет bridge.ready.
7. Backend переводит Device Bridge в состояние ready и разрешает передачу команд.

Успешный запуск процесса ОС сам по себе не означает готовность Bridge. Готовность подтверждается только handshake и bridge.ready.

### 8.5. Heartbeat и reconnect

Heartbeat контролирует IPC-соединение и состояние процесса. Потеря heartbeat переводит Bridge в degraded/offline, прекращает отправку новых команд и запускает политику восстановления.

После восстановления канала Bridge повторно сообщает актуальное состояние runtime и декларации устройств. Backend сверяет их со своим постоянным реестром.

---

## 9. Жизненный цикл процесса Bridge

Backend управляет процессом Bridge. Рекомендуется переиспользовать проверенные принципы существующего internal/mediacompanion, но не копировать его HTTP health-check как основной механизм готовности.

Backend должен:
- запускать настроенный исполняемый файл с контролируемой рабочей директорией;
- передавать конфигурацию и путь IPC безопасным способом;
- отслеживать завершение дочернего процесса;
- ждать handshake и readiness с ограниченным timeout;
- контролировать heartbeat;
- выполнять ограниченные перезапуски с backoff;
- отправлять shutdown и ждать завершения;
- принудительно завершать процесс после истечения shutdown timeout;
- корректно собирать дочерний процесс, исключая zombie process.

Если Bridge не запустился, Backend остаётся работоспособным, но подсистема устройств получает состояние unavailable/degraded. Новые команды устройствам отклоняются понятной ошибкой. Сбой Bridge не должен останавливать независимые функции Backend.

Количество перезапусков, интервалы, startup timeout и shutdown timeout должны быть конфигурируемыми и валидироваться.

---

## 10. Драйверы и runtime

На первом этапе драйверы — встроенные Go-пакеты в одном бинарном файле Bridge. Динамическая загрузка исполняемых модулей не используется.

Каждый драйвер должен предоставлять согласованный набор операций:
- обнаружение или подключение устройств;
- получение декларации устройства и capabilities;
- выполнение поддерживаемой команды;
- приём событий и телеметрии;
- получение/обновление состояния при возможности;
- закрытие подключения и освобождение ресурсов.

Bridge Runtime управляет экземплярами драйверов и активными подключениями. Router не содержит протокольной логики: он выбирает драйвер и обработчик по runtime-карте. Преобразование в команды протокола выполняется внутри драйвера.

Один драйвер может обслуживать несколько устройств. Несколько драйверов могут предоставлять одинаковые HomeCloud capabilities, но их протокольные реализации остаются независимыми.

## 11. Безопасность

- IPC доступен только локальному пользователю/службе Backend и Bridge.
- Unix socket создаётся в каталоге с ограниченными правами; Windows named pipe получает ACL для нужного пользователя/службы.
- Backend не доверяет декларациям Bridge без валидации.
- Bridge не принимает произвольные команды, отсутствующие в runtime capabilities.
- Параметры команд валидируются и в Backend, и в Bridge/драйвере.
- Секреты сопряжения хранятся с ограниченными правами и никогда не попадают в логи.
- Логи не должны содержать ключи, токены, пароли и полные чувствительные payload.
- Драйверы работают с минимально необходимыми системными привилегиями.
- Внутренний IPC не считается заменой пользовательской авторизации: Backend остаётся точкой проверки прав.
- Текущий Backend WS hello использует device_id/client_type как routing labels, а не криптографическую идентичность. Существующий доверенный LAN/Tailscale периметр нельзя считать полноценной пользовательской авторизацией. Device Bridge не должен ухудшать эту границу или открывать новый сетевой интерфейс.

---

## 12. Совместимость и версии

Нужно различать:
- версию публичного Backend WebSocket API (сейчас v1);
- версию внутреннего IPC-протокола Backend ↔ Bridge;
- версию схемы каталога Capability;
- ревизию декларации capabilities конкретного устройства.

Изменение IPC не должно автоматически менять публичный WS API UI. Backend адаптирует внутренний протокол к публичной модели.

Backend и Bridge согласуют совместимую версию на handshake. При несовместимости Bridge не переходит в ready, а Backend сообщает диагностическую ошибку.

Изменение набора capabilities устройства увеличивает revision его декларации. Команда может содержать ожидаемую revision, чтобы Bridge мог обнаружить устаревшую модель.

## 13. Интеграция с текущим HomeCloud Backend

Проверенная ветка Backend main на commit e252b5bae7f1e7c6999ab2acec7d8ef3df2a55d4 уже содержит:

- internal/commands.Registry — типизированную регистрацию и dispatch команд;
- internal/events.Bus — session-scoped pub/sub для WebSocket-событий;
- internal/connections.Manager — управление активными WS peers и очередями исходящих сообщений;
- internal/devices.Store и таблицу hc_devices — каталог клиентов Backend, подключающихся по WebSocket;
- internal/mediacompanion — пример запуска отдельного процесса, readiness probe, restart policy и graceful shutdown;
- internal/database — SQLite и явную инициализацию схемы.

### 13.1. Что переиспользовать

- Публичный WebSocket JSON v1 и текущую регистрацию команд.
- Event Bus для уведомлений UI о регистрации, состоянии и доступности устройств.
- Существующий SQLite connection и механизм миграций.
- Общие принципы supervisor из mediacompanion.
- Структурированные логи и context/timeouts.

### 13.2. Что не переиспользовать напрямую

- hc_devices нельзя считать реестром IoT-устройств: сейчас он хранит WS-клиентов и их client_type.
- connections.Manager не является маршрутизатором физических устройств: он доставляет сообщения активным WS peers.
- Media Gateway registration через публичный WS не является IPC-контрактом Device Bridge.
- media companion HTTP health endpoint не заменяет Bridge handshake.
- Публичный WS handler не должен содержать протокольную или драйверную логику.

### 13.3. Предполагаемые точки интеграции Backend

- отдельный пакет домена физических устройств и его Registry/Service;
- отдельный IPC package для локального канала;
- отдельный supervisor Device Bridge;
- регистрация публичной команды устройств через существующий commands.Registry;
- публикация device events через существующий events.Bus;
- отдельные SQLite-таблицы и миграции, не ломающие hc_devices.

Конкретные имена пакетов и таблиц фиксируются при реализации после проверки актуального дерева и тестов Backend.

## 14. Сквозной сценарий v1: лампочка

Минимальный acceptance scenario:

1. Backend запускает Device Bridge и получает bridge.ready.
2. Драйвер обнаруживает лампочку.
3. Bridge отправляет декларацию: функциональный тип light, capabilities switch и brightness.
4. Backend проверяет декларацию по своим каталогам и сохраняет устройство.
5. Backend публикует событие об изменении реестра.
6. UI запрашивает модель устройства и отображает переключатель и ползунок яркости.
7. Пользователь включает лампу. UI отправляет devices.command в Backend.
8. Backend проверяет устройство, capability switch, команду и разрешения.
9. Backend передаёт абстрактную команду через IPC.
10. Bridge Router находит лампу и нужный драйвер.
11. Драйвер выполняет протокольную операцию.
12. Bridge передаёт результат Backend.
13. Backend обновляет состояние и публикует событие.
14. Аналогично проверяется изменение яркости.
15. Команда brightness для устройства без такой capability отклоняется Backend до IPC.

Для первого сквозного теста допустим симулятор драйвера. После проверки контрактов он заменяется реальным драйвером без изменения публичного UI API и доменной модели Backend.

## 15. Этапы реализации

1. Утвердить доменную модель Device Type, Capability, Entity, Device и State.
2. Утвердить JSON Schema IPC v1 и правила фреймирования.
3. Реализовать IPC endpoint Backend и Bridge handshake.
4. Реализовать Bridge supervisor и lifecycle процесса.
5. Реализовать Bridge runtime и тестовый драйвер лампочки.
6. Реализовать Backend регистрацию деклараций и отдельные реестры.
7. Реализовать командную проверку Backend и Bridge Router.
8. Реализовать передачу state/telemetry и публикацию UI events.
9. Подключить существующий WebSocket UI к новой доменной модели.
10. Провести интеграционный тест полного сценария лампочки.
11. После этого добавлять реальные протоколы и драйверы.

Каждый этап должен иметь unit и интеграционные тесты. Контрактные тесты Backend ↔ Bridge должны проверять несовместимую версию, некорректные сообщения, потерю IPC, повторную регистрацию, устаревшую revision, недоступное устройство и ошибку исполнения команды.

## 16. Решения, требующие окончательного согласования

Следующие детали нельзя считать окончательно утверждёнными только на основании этого документа:

1. **Идентификатор физического устройства.** Кто формирует стабильный device_id и как Backend сопоставляет повторное обнаружение с уже зарегистрированной записью, не зная протокольных идентификаторов.
2. **Неизвестный Device Type/Capability.** Отклонять декларацию целиком, регистрировать устройство в ограниченном состоянии или поддерживать процедуру ручного сопоставления.
3. **Транспорт IPC на Windows.** Подтвердить named pipe и выбрать реализацию/зависимость; Linux вариант — Unix domain socket.
4. **Фреймирование IPC.** Подтвердить 4-byte length-prefixed JSON и лимит кадра.
5. **Модель команд.** Подтвердить синхронный ответ для быстрых команд и асинхронные статусы/события для операций, которые требуют длительного подтверждения.
6. **Политика сопряжения и авторизации.** Согласовать, как текущая модель безопасности Backend будет применяться к обнаруженным физическим устройствам и пользователям UI.
7. **Каталог Capability.** Утвердить первые стандартные capabilities и их схемы, начиная с switch и brightness.

Эти вопросы должны быть закрыты до фиксации окончательных JSON Schema и начала реализации соответствующих частей.

## 17. Критерии готовности архитектуры v1

Архитектура считается согласованной, когда определены:

- границы ответственности Backend, Bridge, драйвера и UI;
- модель Device Type / Capability / Entity / State;
- правила регистрации и обновления устройства;
- IPC transport, framing, handshake, heartbeat и shutdown;
- формат команды, маршрутизация, статусы и ошибки;
- формат телеметрии и событий;
- модель доступных UI действий с учётом capabilities и permissions;
- правила совместимости версий и восстановления после сбоев;
- сквозной тест лампочки.

**Главное правило:** Backend знает, что устройство может делать и кому разрешено это делать. Bridge знает, как конкретное устройство это делает. UI знает только модель, которую предоставляет Backend.
