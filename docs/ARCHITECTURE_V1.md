## 1. Цель и границы

HomeCloud Device Bridge — отдельный Go-процесс на том же узле, что и HomeCloud Backend. Он обнаруживает физические устройства, поддерживает их протокольные подключения, преобразует абстрактные команды HomeCloud в операции конкретного драйвера и нормализует поступающие от устройств данные.

**Главный принцип:** Backend владеет постоянной идентичностью и логической моделью HomeCloud-устройств. Bridge владеет обнаружением, протокольной идентичностью и runtime-состоянием физических устройств. UI работает только с Backend.

### 1.1. Backend отвечает за

- постоянный HomeCloud `device_id` и логический реестр физических устройств;
- каталог типов устройств и стандартных возможностей HomeCloud;
- проверку и сохранение деклараций устройств, capabilities и сущностей;
- пользовательские метаданные, комнаты, разрешения и нормализованное состояние;
- публичный API и WebSocket-контракт для UI;
- проверку допустимости команд и маршрутизацию команд в Bridge;
- управление процессом Bridge и состоянием IPC-канала.

Backend не использует существующую таблицу `hc_devices` для физических устройств: она остаётся реестром клиентов WebSocket.

### 1.2. Device Bridge отвечает за

- обнаружение физических устройств через локальные интеграции;
- собственный реестр физических устройств и их протокольной идентичности;
- стабильный локальный ключ устройства в пределах интеграции, когда протокол его предоставляет;
- постоянное сопоставление локальной идентичности с выданным Backend `device_id`;
- протокольные подключения и их жизненный цикл;
- встроенные Go-драйверы и маршрутизацию к ним;
- фактические capabilities, доступные драйверу;
- runtime-доступность, соединения и обработку событий;
- преобразование абстрактных команд в протокольные операции;
- передачу в Backend обнаружений, изменений состояния и результатов команд.

Реестр Bridge не заменяет Backend Registry: он нужен для связи с физическим устройством, в том числе когда оно временно недоступно.

### 1.3. UI отвечает за

- получение модели устройств и доступных возможностей от Backend;
- отображение элементов управления на основании стандартных Capability;
- отправку команд Backend;
- отображение состояния, доступности, ошибок и результатов исполнения.

UI не подключается к Bridge и не знает о драйверах, протоколах, адресах устройств или внутренних идентификаторах протокола.

### 1.4. Вне области v1

- динамически загружаемые бинарные плагины;
- отдельный сетевой API Bridge;
- прямое взаимодействие UI ↔ Bridge;
- обязательные облака производителей;
- универсальный движок автоматизаций;
- хранение полной истории телеметрии в Bridge;
- удалённое подключение Bridge с другого узла. В v1 Backend и Bridge находятся на одном хосте.

## 2. Общая схема

```
Физическое устройство
        ↕ протокол / pairing
Интеграция и драйвер Device Bridge
        ↕
Bridge Device Registry (SQLite)
  ├── integration_id + native_device_id
  ├── local_id
  ├── runtime connection / availability
  ├── driver capabilities
  └── mapping: local_id ↔ HomeCloud device_id
        ↕ локальный Backend WebSocket JSON v1 (loopback)
HomeCloud Backend
  ├── hc_devices: WS-клиенты (включая системный Bridge peer)
  ├── Physical Device Registry (SQLite)
  ├── Device Type / Capability Catalog
  ├── Device State / History
  ├── Pairing and Registration Service
  └── Command Validation / Authorization / Event Bus
        ↕ WebSocket v1
      HomeCloud UI
```

### 2.1. Назначение реестров

**Bridge Device Registry** — реестр физических экземпляров с точки зрения интеграций и драйверов. Он хранит локальную identity, сведения об источнике обнаружения, привязку к драйверу, runtime-состояние и сопоставление с HomeCloud ID. Запись не удаляется только из-за потери соединения с устройством.

**Backend Physical Device Registry** — постоянный каталог сопряжённых физических устройств HomeCloud. Он хранит выданный Backend `device_id`, тип, подтверждённые нормализованные capabilities/entities, пользовательские данные, разрешения и последнее известное состояние. Именно этот реестр читает UI.

\*\*Существующий \*\*`hc_devices` — реестр WebSocket-клиентов Backend. В нём может присутствовать системный WS peer Device Bridge, но физические устройства в него не записываются.

Это три отдельных домена: два реестра физических устройств с разными задачами и один реестр WS-клиентов.

### 2.2. Потоки данных

1. Обнаружение кандидата: устройство в режиме сопряжения → драйвер → временный candidate в Bridge → Backend → UI.
2. Выбор пользователя: UI → Backend → Bridge подтверждает выбранный candidate и выполняет протокольное сопряжение.
3. Регистрация: Bridge сохраняет локальную запись → передаёт Backend identity claim и декларацию → Backend проверяет контракты, назначает `device_id` → Bridge сохраняет mapping.
4. Повторное обнаружение: Bridge находит прежнюю локальную identity и mapping; Backend обновляет availability/metadata без нового выбора и без создания дубля.
5. Команда: UI → Backend WS → проверка capability/schema/permissions → локальный WS → Bridge Router → драйвер → устройство.
6. Состояние и результат: устройство/драйвер → Bridge → Backend → State Registry / Event Bus → UI.

Временное отключение не удаляет постоянные записи. Backend сохраняет идентичность и последнее известное состояние. Физическое исполнение команды возможно только при доступном Bridge и доступном устройстве. Отложенная очередь команд для offline-устройств в v1 не предусматривается.

## 3. Контракт Backend ↔ UI

Backend сохраняет существующий публичный протокол WebSocket JSON v1. Новое подключение UI или новый публичный порт для Device Bridge не требуются.

Существующий конверт сообщения Backend использует поля v, id, type, action и data. Новые команды устройств регистрируются через существующий commands.Registry, а события публикуются через существующий events.Bus.

### 3.1. Получение устройств

UI получает список устройств и их UI-модель через команду Backend. Модель должна содержать:

- стабильный device\_id;
- функциональный device\_type;
- отображаемые метаданные: имя, производитель, модель;
- фактические capabilities;
- сущности и их схемы;
- текущее состояние и время обновления;
- доступные для текущего пользователя действия.

Состав доступных действий вычисляет Backend. Он учитывает одновременно фактические возможности устройства и разрешения пользователя.

### 3.2. Отображение UI

Capability — стандартная функция HomeCloud, а не имя протокольной команды.

Backend предоставляет UI идентификаторы и схемы известных возможностей. UI сопоставляет их со своими штатными компонентами. Например:

| Capability | Возможное представление |
| --- | --- |
| switch | переключатель питания |
| brightness | ползунок яркости |
| color | выбор цвета |
| color\_temperature | настройка цветовой температуры |
| power\_monitoring | показатели мощности, напряжения и тока |
| temperature | значение температуры |
| humidity | значение влажности |

Bridge не передаёт произвольный HTML, React-компоненты или инструкции на исполнение UI-кода.

Неизвестная UI возможность не должна ломать экран: UI может показать базовые метаданные устройства и пропустить неподдерживаемый виджет.

### 3.3. Команда UI

Пример запроса на изменение яркости:

```
{
  "v": 1,
  "id": "ui-request-001",
  "type": "command",
  "action": "devices.command",
  "data": {
    "device_id": "light-001",
    "capability_id": "brightness",
    "command_id": "set",
    "parameters": {
      "value": 75
    }
  }
}
```

Backend проверяет:

1. Существует ли устройство.
2. Зарегистрирована ли у устройства capability brightness.
3. Известна ли команда set в каталоге этой capability.
4. Соответствуют ли параметры её схеме.
5. Разрешено ли текущему субъекту выполнять эту операцию.
6. Доступен ли Bridge.

Если capability отсутствует, Backend отклоняет запрос и не передаёт его Bridge. Например, команда brightness не может быть отправлена розетке, у которой такой возможности нет.

UI не может самостоятельно объявить устройству новую возможность или обойти проверку Backend.

### 3.4. Возможности и разрешения — не одно и то же

- Capability означает, что физическое устройство технически умеет выполнять операцию.
- Permission означает, что текущему пользователю разрешено её выполнять.
- UI получает только итоговый набор доступных действий.

Таким образом, наличие capability не даёт автоматически право управлять устройством.

## 4. Реестры

В системе есть два отдельных реестра физических устройств и отдельный, уже существующий реестр клиентов Backend.

### 4.1. Backend Physical Device Registry

Постоянный логический каталог физических устройств HomeCloud. Владелец — Backend, хранение — отдельные таблицы SQLite. Таблица `hc_devices` не переиспользуется.

Запись содержит:

- стабильный `device_id`, назначенный Backend;
- функциональный тип HomeCloud;
- пользовательское имя и пользовательские метаданные;
- производителя, модель, аппаратную ревизию и прошивку, если известны;
- подтверждённые capabilities и сущности;
- состояние регистрации и доступности;
- время первого обнаружения и последнего контакта;
- последнее известное состояние сущностей.

Backend Registry сохраняет устройство при временной потере связи. Доступность меняется отдельно от существования записи.

### 4.2. Bridge Device Registry

Реестр Bridge описывает физические экземпляры с точки зрения интеграций и драйверов. Он должен сохранять данные между перезапусками Bridge.

Минимальная запись:

- внутренний `local_id`;
- `integration_id` — namespace интеграции/протокола;
- `native_device_id` или другой стабильный identity key, предоставленный интеграцией;
- driver/integration metadata;
- обнаруженные native metadata и фактические capabilities;
- runtime availability/connection state;
- связанный HomeCloud `device_id`, полученный от Backend;
- timestamps обнаружения и последнего контакта.

Ключ сопоставления строится в namespace интеграции, а не из одного MAC/IP. Если протокол не предоставляет надёжный постоянный идентификатор, драйвер должен явно сообщить об ограниченной надёжности identity claim; автоматическое объединение неоднозначных записей запрещено.

Bridge Registry отвечает за повторное нахождение физического экземпляра. Backend ID остаётся каноническим идентификатором HomeCloud.

### 4.3. Device Type Registry

Каталог функциональных типов HomeCloud: `light`, `smart_plug`, `temperature_sensor`, `motion_sensor` и другие. Device Type описывает назначение устройства, но не гарантирует наличие конкретных возможностей. Производитель, модель, аппаратная ревизия и версия прошивки остаются metadata конкретного экземпляра.

### 4.4. Capability Registry

Канонический каталог стандартных возможностей HomeCloud. Для каждой Capability контракт определяет:

- стабильный `capability_id` и версию контракта;
- перечень команд и их идентификаторы;
- типизированные параметры команд, обязательность, диапазоны и ограничения;
- Entities, которые capability предоставляет или которыми управляет;
- типы значений, единицы измерения и правила нормализации;
- UI metadata для отображения стандартными компонентами HomeCloud;
- при необходимости — семантические требования к permissions.

Capability описывает функциональный контракт, а не реализацию протокола. Например, `brightness.set` имеет одинаковую семантику для Zigbee- и Matter-лампы, хотя драйверы выполняют разные протокольные операции.

Backend является точкой принятия решения: он проверяет объявленные устройством capabilities по каталогу и формирует разрешённые действия с учётом permissions. Bridge сообщает фактическую поддержку и повторно проверяет её перед исполнением.

### 4.5. Device State Registry

Backend хранит последнее известное состояние сущностей устройства. Значение состояния отделено от описания возможности: поддержка brightness не означает, что текущее значение яркости известно.

Каждое обновление состояния должно иметь `device_id`, `entity_id`, типизированное значение, время измерения/получения и источник/версию обновления для защиты от устаревших данных.

### 4.6. История телеметрии

Текущее состояние и история — разные задачи. История телеметрии может сохраняться отдельным механизмом Backend с политикой хранения и ограничением объёма. Bridge передаёт измерения, но не определяет политику долговременного хранения.

### 4.7. Общий пакет Device Contracts

**Принято решение: вариант B — общие контракты Backend и Bridge.**

Определения Device Type, Capability и Entity являются версионируемыми контрактами HomeCloud и поставляются через общий Go-пакет, который импортируют Backend и Device Bridge. Пакет содержит только общие определения и не содержит реализаций протоколов или драйверов.

Состав общего пакета:

- Go-типы и константы стабильных идентификаторов;
- версии контрактов и типизированные структуры деклараций;
- JSON Schema для деклараций устройств, команд, параметров и значений Entities;
- общие ограничения, enum-значения, единицы измерения и правила валидации;
- нейтральные UI metadata, необходимые для стандартного представления capability;
- совместимые примеры и contract tests / test fixtures.

Backend использует этот пакет как основу своего Device Type / Capability Catalog и остаётся авторитетной стороной валидации, регистрации и принятия решений. Bridge использует те же типы и схемы для формирования деклараций и проверки команд перед передачей драйверу. Общий пакет не предоставляет Bridge право самостоятельно регистрировать устройства или разрешать пользовательские действия.

Драйверы остаются внутри Device Bridge. Они преобразуют стандартные команды HomeCloud в операции конкретного протокола и нормализуют входящие данные. В общий пакет не включаются Zigbee/Matter/Bluetooth API, сетевые клиенты, runtime handlers или код выполнения команд.

Общий пакет должен иметь собственную версию и правила обратной совместимости. Backend и Bridge согласуют совместимые версии контрактов; несовместимая версия не должна молча интерпретироваться как поддерживаемая.

### 4.8. Где хранятся определения и экземпляры

Необходимо разделять **статические определения контрактов** и **динамические данные конкретных устройств**.

- Статические определения Device Type / Capability / Entity хранятся в общем версионируемом Go-пакете (исходные JSON Schema и Go-типы). Они поставляются вместе с Backend и Bridge и не создаются заново при каждом обнаружении устройства.
- Backend SQLite хранит экземпляры физических устройств, подтверждённые для них capabilities и их revision, identity mappings, пользовательские metadata, rooms, permissions, нормализованное состояние и историю согласно политике хранения.
- Bridge SQLite хранит локальные экземпляры, integration/native identity, driver metadata, фактическую декларацию возможностей, данные для восстановления и mapping на HomeCloud `device_id`. Временные соединения и runtime-состояние не обязаны переживать перезапуск.
- Фиксированные поля, по которым выполняются поиск, ограничения и связи, следует хранить в нормализованных таблицах SQLite. Расширяемые metadata и декларации допустимо хранить в JSON-полях, сохраняя версию и проверяя содержимое по общим схемам. Конкретный набор таблиц и индексов определяется при проектировании миграций.
- Текущее состояние Entities хранится отдельно от декларации Capability: наличие возможности не означает, что её текущее значение известно.

Итого: общий пакет — источник определения смысла и формата; Backend SQLite — источник истины о HomeCloud-экземплярах и пользовательской конфигурации; Bridge SQLite — источник истины о локальной протокольной привязке и восстановлении драйверов.

### 4.9. Существующий реестр клиентов `hc_devices`

`internal/devices.Store` и таблица `hc_devices` в текущем Backend относятся к клиентам HomeCloud, подключающимся по WebSocket. Они содержат `device_id`, `client_type`, имя и timestamps клиентского подключения.

Эта модель не является реестром IoT/физических устройств и остаётся без изменений. Для физических устройств создаётся отдельный домен и отдельные таблицы SQLite.

## 5. Контракт регистрации и повторного обнаружения устройства

Регистрация физического устройства в постоянном Backend Physical Device Registry выполняется только после того, как пользователь выбрал обнаруженный candidate. Сам факт обнаружения не создаёт сопряжённое HomeCloud-устройство и не даёт права отправлять ему команды.

Bridge сообщает Backend identity claim и декларацию устройства после успешного протокольного сопряжения. В декларации передаются локальная идентичность в namespace интеграции, метаданные, функциональный тип и фактические capabilities. Bridge не назначает глобальный HomeCloud `device_id`.

### 5.1. Первичная регистрация после выбора

1. Пользователь физически переводит устройство в режим сопряжения.
2. Драйвер обнаруживает устройство и формирует временный candidate.
3. Bridge передаёт candidate в Backend; Backend делает его доступным UI для выбора.
4. Пользователь выбирает конкретное устройство в UI.
5. Backend проверяет право пользователя на сопряжение и передаёт Bridge запрос на подтверждение выбранного candidate.
6. Bridge проверяет, что candidate ещё существует и не истёк, затем выполняет необходимую процедуру протокольного сопряжения.
7. После успешного сопряжения Bridge создаёт или обновляет запись в Bridge Device Registry.
8. Bridge отправляет Backend identity claim, metadata, Device Type и декларацию capabilities.
9. Backend проверяет identity, Device Type, capabilities и entities по общим Device Contracts.
10. Backend ищет прежнюю identity mapping. Если это ранее известное устройство, возвращается существующий `device_id`; иначе Backend назначает новый постоянный `device_id`.
11. Backend сохраняет запись и возвращает результат регистрации, назначенный `device_id`, подтверждённые capabilities и revision.
12. Bridge сохраняет mapping `local_id ↔ device_id`. Backend публикует событие изменения реестра, UI отображает сопряжённое устройство.

До выбора пользователя candidate остаётся временной записью обнаружения. Он не является полноценной записью Physical Device Registry и не может принимать команды управления.

### 5.2. Повторное обнаружение и отключение

Повторное обнаружение ранее сопряжённой локальной identity не требует повторного выбора пользователя. Bridge находит прежнюю запись и mapping, Backend обновляет availability, metadata и декларацию в рамках существующего `device_id`.

При временном отключении Bridge сообщает Backend об изменении availability; обе постоянные записи и последнее известное состояние сохраняются.

Если Bridge перезапустился, он восстанавливает persistent registry и mapping, затем сверяет устройства с Backend. Если локальная база Bridge потеряна, Backend всё ещё сохраняет HomeCloud device record и identity claims; Bridge может восстановить связь по повторному identity claim, если он достаточно надёжен.

### 5.3. Неустойчивая или конфликтующая идентичность

MAC-адрес и IP-адрес сами по себе не считаются универсальным stable identity. Если интеграция не предоставляет надёжный ключ или два устройства претендуют на одну identity, Backend не должен автоматически объединять их. Такая запись переводится в состояние, требующее разрешения конфликта или явного сопоставления пользователем.

### 5.4. Пример identity claim

```json
{
  "integration_id": "zigbee",
  "native_device_id": "coordinator-specific-stable-id",
  "device_type": {
    "id": "light",
    "version": 1
  },
  "metadata": {
    "manufacturer": "Example",
    "model": "Bulb A",
    "firmware_version": "1.2.0"
  },
  "capability_revision": 1,
  "capabilities": [
    { "id": "switch", "version": 1 },
    { "id": "brightness", "version": 1 }
  ]
}
```

Пример показывает структуру декларации, но не заменяет JSON Schema общего Device Contracts пакета. Backend проверяет идентификаторы и версии по поставляемому каталогу, затем возвращает назначенный `device_id` и результат принятия каждой capability. Неизвестные или несовместимые capabilities не становятся исполняемыми. Backend ID не берётся из identity claim.

## 6. Сопряжение и выбор устройства пользователем

Сопряжение в HomeCloud — полуавтоматический процесс. Пользователь инициирует физическую доступность устройства, переводя его в режим сопряжения, затем выбирает нужное устройство из обнаруженных. Все последующие технические операции выполняются автоматически Bridge и Backend.

### 6.1. Основной сценарий

1. Пользователь переводит физическое устройство в pairing mode способом, предусмотренным производителем или протоколом.
2. Включённая интеграция Bridge обнаруживает устройство и создаёт временный candidate.
3. Backend получает candidate и передаёт его в UI. UI показывает доступную идентифицирующую информацию: название, тип, производителя, модель, интеграцию и дополнительные признаки, если они доступны.
4. Пользователь выбирает нужный candidate.
5. Backend передаёт Bridge подтверждение выбора.
6. Bridge выполняет protocol-level pairing/commissioning, включая обязательный обмен ключами, PIN, QR или иные предусмотренные протоколом действия.
7. После успешного сопряжения запускается постоянная регистрация по разделу 5.
8. Устройство появляется в обычном списке устройств HomeCloud и становится доступным для управления в рамках подтверждённых capabilities и permissions.

Пользователь выбирает физическое устройство, а не отдельные capabilities и не параметры внутренней регистрации.

### 6.2. Временные candidates

- Candidate создаётся только на время обнаружения и сопряжения.
- Candidate имеет временный `candidate_id`, который не является HomeCloud `device_id`.
- Candidate не сохраняется как сопряжённое устройство в Backend Physical Device Registry.
- Candidate должен иметь ограниченный срок жизни. После исчезновения устройства, завершения pairing window или истечения TTL он становится недоступным для выбора.
- Backend перед подтверждением выбора проверяет, что candidate ещё актуален; Bridge повторно проверяет это перед началом протокольной операции.
- Если candidate уже исчез, Backend возвращает понятную ошибку и предлагает повторить обнаружение; автоматическое создание записи по устаревшему candidate запрещено.

Точный TTL и детали обнаружения задаются конфигурацией интеграции и фиксируются в Bridge Protocol Specification.

### 6.3. Состояния сопряжения

| Состояние | Значение |
| --- | --- |
| `discovered` | Bridge обнаружил candidate; пользователь ещё не выбрал его |
| `pairing_requested` | Backend передал подтверждённый пользователем выбор |
| `pairing_in_progress` | Bridge выполняет протокольное сопряжение |
| `registration_pending` | Протокольное сопряжение завершено, Backend проверяет декларацию |
| `paired` | Устройство зарегистрировано и имеет постоянный `device_id` |
| `pairing_failed` | Протокольное сопряжение или регистрация завершились ошибкой |
| `expired` | Candidate исчез или истёк до выбора/завершения |

Эти состояния не заменяют availability физического устройства: сопряжённое устройство может быть `offline`, оставаясь зарегистрированным.

### 6.4. Повторное обнаружение

Если Bridge распознаёт ранее сопряжённое устройство по сохранённой устойчивой identity, пользовательский выбор не требуется. Bridge восстанавливает прежний mapping, Backend обновляет состояние существующей записи. Если identity конфликтует или не может быть подтверждена, автоматическое объединение запрещено.

### 6.5. Безопасность сопряжения

Выбор candidate в UI не заменяет защиту протокола. Bridge обязан выполнять предусмотренную протоколом аутентификацию/commissioning и безопасно хранить pairing credentials. PIN, ключи, токены и QR-derived secrets не должны попадать в логи. Backend проверяет права пользователя на запуск сопряжения; UI не подключается к Bridge напрямую.

## 7. Телеметрия и состояние

Драйвер преобразует данные протокола в нормализованные значения HomeCloud. Bridge передаёт Backend device\_id, entity\_id, значение и временные метки.

Backend:

1. Проверяет, что сущность зарегистрирована у данного устройства.
2. Проверяет тип значения и единицу измерения по каталогу.
3. Отбрасывает некорректные или устаревшие обновления.
4. Обновляет последнее известное состояние.
5. При включённой политике записывает измерение в историю.
6. Публикует событие для подписчиков UI.

Пример нормализованного измерения:

```
{
  "device_id": "plug-001",
  "entity_id": "power",
  "value": 125.4,
  "unit": "W",
  "measured_at": "2026-11-23T10:20:30Z"
}
```

Bridge не выбирает, сколько дней хранить историю энергопотребления, и не становится источником данных для Monitoring напрямую.

События Event Bus являются механизмом доставки обновлений, а не долговременным хранилищем. После переподключения UI должен иметь возможность получить актуальный snapshot из Backend.

## 8. Backend ↔ Bridge: управляющий канал

Для Device Bridge переиспользуется существующая модель управляющего взаимодействия с отдельным Media Gateway: локальный Backend WebSocket JSON v1, отдельный HTTP health endpoint и lifecycle дочернего процесса через stdin EOF. Не вводим Unix Socket / Named Pipe и не создаём второй независимый IPC-стек.

### 8.1. Управляющий WebSocket

Bridge подключается к локальному WebSocket endpoint HomeCloud Backend по loopback. Используется существующий WebSocket JSON v1 и тот же конверт сообщений Backend:

```json
{
  "v": 1,
  "id": "request-id",
  "type": "command",
  "action": "bridge.status",
  "data": {}
}
```

Применяются существующие правила протокола: request ID и correlation, типы command/result/error/event, JSON payload и контроль версии. Канал используется для service registration, pairing candidates и выбора, регистрации физических устройств, команд, состояния, событий и heartbeat. Никакие медиаданные через него не передаются.

Bridge подключается именно к локальному Backend loopback endpoint. Отдельный публичный порт Bridge не открывается.

### 8.2. Идентификация и регистрация Bridge

При подключении Bridge проходит стандартный WS handshake и идентифицируется как системный peer с:

- `client_type = "device_bridge"`;
- фиксированным `device_id = "homecloud-device-bridge"`;
- активной WS session;
- loopback remote address.

Существующий Backend WS handler регистрирует подключённый peer в `connections.Manager` и в `hc_devices` через текущий `devices.Store`. Это допустимо, поскольку `hc_devices` хранит WS-клиентов. Запись Bridge там обозначает системное клиентское соединение, а не физическое устройство.

После стандартного handshake Bridge вызывает отдельный privileged registration action. Рабочее имя action для v1: `device.bridge.register`. По образцу уже реализованного `media.gateway.register` Backend проверяет enable flag, loopback remote IP, фиксированные `client_type` и `device_id`, а также ненулевой session ID. Точное имя action и payload фиксируются в Bridge Protocol Specification и Backend implementation contract.

Регистрация процесса Bridge и регистрация физических устройств — разные операции. Физические устройства никогда не добавляются в `hc_devices`; они регистрируются в отдельном Backend Physical Device Registry.

Важно: текущая WS identity — routing identity, а не криптографическое доказательство исполняемого файла. Loopback ограничивает поверхность подключения, но само по себе не является криптографической аутентификацией процесса.

### 8.3. Группы сообщений

| Направление | Сообщения / actions | Назначение |
| --- | --- | --- |
| Bridge → Backend | стандартный hello | Handshake и identity системного peer |
| Bridge → Backend | `device.bridge.register` | Регистрация системной службы Bridge |
| Bridge → Backend | `bridge.ready` | Runtime Bridge готов принимать команды |
| Обе стороны | heartbeat / heartbeat.ack | Контроль управляющего канала |
| Bridge → Backend | pairing candidate discovered/updated | Временные обнаруженные кандидаты |
| Backend → Bridge | pairing selection/confirm | Выбор candidate пользователем |
| Bridge → Backend | pairing result | Результат протокольного сопряжения |
| Bridge → Backend | device registration claim | Identity claim и декларация после pairing |
| Backend → Bridge | device registration result | Назначенный HomeCloud `device_id` и результат валидации |
| Backend → Bridge | device command | Абстрактная команда физическому устройству |
| Bridge → Backend | command accepted / command result | Принятие и фактический результат исполнения |
| Bridge → Backend | device state changed | Нормализованное состояние |
| Bridge → Backend | device availability changed | Доступность физического устройства |
| Backend → Bridge | shutdown через lifecycle | Контролируемое завершение процесса |

Названия pairing и device actions в таблице — семантические группы. Точные action names, поля, error codes и JSON Schema фиксируются в спецификации Bridge ↔ Backend. Все сообщения используют существующий WS JSON v1 envelope, а не новый framing-протокол.

### 8.4. Handshake и готовность

1. Backend запускает дочерний процесс Bridge.
2. Bridge запускается в supervised-режиме и подключается к локальному Backend WS endpoint.
3. Bridge отправляет стандартный hello с service identity.
4. Backend регистрирует WS peer, затем проверяет отдельную service registration команду.
5. Bridge восстанавливает persistent registry и runtime драйверов.
6. Bridge выполняет reconcile с Backend и отправляет `bridge.ready`.
7. Backend считает подсистему готовой принимать команды.

Запуск процесса ОС или успешный HTTP health probe сам по себе не означает, что Bridge зарегистрирован в Backend и готов обслуживать устройства.

### 8.5. Heartbeat и reconnect

Heartbeat управляющего канала выполняется по существующим правилам Backend WS v1. При потере соединения Bridge переподключается с ограниченным backoff. Backend не должен считать физические устройства удалёнными только из-за кратковременного reconnect Bridge: постоянные записи сохраняются, а availability обновляется согласно состоянию Bridge и последним данным драйверов.

После восстановления канала Bridge сверяет свои persistent identity mappings с Backend, повторно регистрирует service session, если требуется, и отправляет reconcile/snapshot. Повторная регистрация не должна создавать дубликаты физических устройств.

## 9. Жизненный цикл процесса Bridge

Backend управляет процессом Bridge по модели существующего Media Gateway supervisor.

Backend должен:

- запускать настроенный исполняемый файл через `exec.Command` с контролируемой рабочей директорией и конфигурацией;
- создавать stdin pipe для supervised child process;
- отслеживать завершение дочернего процесса через `cmd.Wait()`;
- проверять локальный HTTP health endpoint Bridge при старте и периодически;
- отдельно контролировать WS handshake, service registration, heartbeat и `bridge.ready`;
- считать Bridge готовым только после успешного процесса readiness + WS registration + runtime readiness;
- выполнять ограниченные перезапуски с backoff;
- при штатной остановке закрывать stdin: EOF инициирует graceful shutdown Bridge;
- ждать завершения в пределах shutdown timeout, затем принудительно завершать процесс и корректно собирать его.

HTTP health endpoint подтверждает живость процесса и базовое состояние runtime, но не заменяет WS handshake, регистрацию системного peer и `bridge.ready`. Управляющие сообщения идут только по Backend WebSocket JSON v1.

Если Bridge не запустился или потерял управляющее соединение, Backend остаётся работоспособным, но подсистема устройств получает состояние unavailable/degraded. Новые команды устройствам отклоняются понятной ошибкой. Сбой Bridge не должен останавливать независимые функции Backend.

Параметры executable, working directory, health URL, startup timeout, health interval, restart backoff и shutdown timeout должны быть конфигурируемыми и валидироваться. Конкретная схема конфигурации описывается в Development Guide.

## 10. Драйверы и runtime

На первом этапе драйверы — встроенные Go-пакеты в одном бинарном файле Bridge. Динамическая загрузка исполняемых модулей не используется.

Каждый драйвер должен предоставлять согласованный набор операций:

- обнаружение или подключение устройств;
- получение identity claim и декларации устройства;
- выполнение поддерживаемой команды;
- приём событий и телеметрии;
- получение/обновление состояния при возможности;
- закрытие подключения и освобождение ресурсов.

Bridge Runtime управляет экземплярами драйверов и активными подключениями. Bridge Device Registry хранит постоянную локальную идентичность и сопоставление с Backend `device_id`; runtime connection state обновляется независимо и может быть offline при сохранённой записи.

Router находит устройство по HomeCloud `device_id` через mapping Bridge Registry, затем выбирает нужный драйвер и runtime handler. Router не содержит протокольной логики: преобразование в команды протокола выполняется внутри драйвера.

Один драйвер может обслуживать несколько устройств. Несколько драйверов могут предоставлять одинаковые HomeCloud capabilities, но их протокольные реализации остаются независимыми.

## 11. Безопасность

- IPC доступен только локальному пользователю/службе Backend и Bridge.
- Управляющий WebSocket доступен только на локальном loopback endpoint; Bridge не открывает собственный публичный сетевой порт.
- Backend не доверяет декларациям Bridge без валидации.
- Bridge не принимает произвольные команды, отсутствующие в runtime capabilities.
- Параметры команд валидируются и в Backend, и в Bridge/драйвере.
- Секреты сопряжения хранятся с ограниченными правами и никогда не попадают в логи.
- Логи не должны содержать ключи, токены, пароли и полные чувствительные payload.
- Драйверы работают с минимально необходимыми системными привилегиями.
- Внутренний IPC не считается заменой пользовательской авторизации: Backend остаётся точкой проверки прав.
- Текущий Backend WS hello использует device\_id/client\_type как routing labels, а не криптографическую идентичность. Существующий доверенный LAN/Tailscale периметр нельзя считать полноценной пользовательской авторизацией. Device Bridge не должен ухудшать эту границу или открывать новый сетевой интерфейс.

## 12. Совместимость и версии

Необходимо различать независимые версии:

- публичного Backend WebSocket API (сейчас v1);
- управляющего Backend ↔ Bridge протокола (использует существующий WS JSON v1 envelope);
- общего Device Contracts пакета;
- отдельных контрактов Device Type / Capability / Entity;
- декларации capabilities конкретного экземпляра устройства (`capability_revision`).

Общий Device Contracts пакет версионируется как Go-модуль/зависимость. Изменения контрактов проходят проверку обратной совместимости и contract tests. Backend и Bridge должны собираться с совместимыми версиями пакета; совместимость также проверяется при handshake, чтобы исключить запуск несовместимых бинарников.

Изменение набора capabilities конкретного устройства увеличивает его `capability_revision`. Версия определения capability и revision декларации устройства — разные величины: первая меняется при изменении самого стандарта HomeCloud, вторая — при изменении фактического набора возможностей экземпляра.

Неизвестные версии и поля не должны молча трактоваться как поддерживаемые. Backend остаётся авторитетной стороной проверки и регистрации деклараций; Bridge повторно проверяет текущую revision и runtime-поддержку перед физическим исполнением команды.

Изменение внутреннего контракта не должно автоматически менять публичный UI WS API: Backend адаптирует внутреннюю модель к публичной модели HomeCloud.

## 13. Интеграция с текущим HomeCloud Backend

Проверенная ветка Backend main на commit e252b5bae7f1e7c6999ab2acec7d8ef3df2a55d4 уже содержит:

- internal/commands.Registry — типизированную регистрацию и dispatch команд;
- internal/events.Bus — session-scoped pub/sub для WebSocket-событий;
- internal/connections.Manager — управление активными WS peers и очередями исходящих сообщений;
- internal/devices.Store и таблицу hc\_devices — каталог клиентов Backend, подключающихся по WebSocket;
- internal/mediacompanion — пример запуска отдельного процесса, readiness probe, restart policy и graceful shutdown;
- internal/database — SQLite и явную инициализацию схемы.

### 13.1. Что переиспользовать

- Публичный WebSocket JSON v1 и текущую регистрацию команд.

- Структурированные логи и context/timeouts.

### 13.2. Что не переиспользовать напрямую

- hc\_devices нельзя считать реестром IoT-устройств: сейчас он хранит WS-клиентов и их client\_type.
- connections.Manager не является маршрутизатором физических устройств: он доставляет сообщения активным WS peers.
- Регистрация процесса Bridge и регистрация физических устройств — разные операции и домены; физические устройства не переносятся в модель WS-клиентов.
- media companion HTTP health endpoint не заменяет Bridge handshake.
- Публичный WS handler не должен содержать протокольную или драйверную логику.

### 13.3. Предполагаемые точки интеграции Backend

- отдельный пакет домена физических устройств и его Registry/Service;
- отдельный IPC package для локального канала;
- отдельный supervisor Device Bridge;
- регистрация публичной команды устройств через существующий commands.Registry;
- публикация device events через существующий events.Bus;
- отдельные SQLite-таблицы и миграции, не ломающие hc\_devices.

Конкретные имена пакетов и таблиц фиксируются при реализации после проверки актуального дерева и тестов Backend.

## 14. Сквозной сценарий v1: сопряжение лампочки и управление

Минимальный acceptance scenario:

1. Backend запускает Device Bridge, проверяет health, WS registration и получает `bridge.ready`.
2. Пользователь переводит Zigbee-лампочку в pairing mode.
3. Драйвер обнаруживает лампочку и создаёт временный candidate.
4. Bridge отправляет candidate Backend; Backend передаёт его UI.
5. UI показывает найденную лампочку. Пользователь выбирает её.
6. Backend проверяет право пользователя и передаёт Bridge подтверждение выбора.
7. Bridge выполняет необходимую протокольную процедуру сопряжения.
8. Bridge сохраняет запись в Bridge Device Registry и отправляет Backend identity claim, функциональный тип `light`, capabilities `switch` и `brightness`.
9. Backend проверяет декларацию по общему Device Contracts, назначает `device_id`, сохраняет запись в Physical Device Registry и возвращает registration result.
10. Bridge сохраняет mapping `local_id ↔ device_id`.
11. Backend публикует событие об изменении реестра; UI отображает переключатель и ползунок яркости.
12. Пользователь включает лампу. UI отправляет `devices.command` в Backend.
13. Backend проверяет устройство, capability `switch`, схему команды и permissions.
14. Backend передаёт абстрактную команду через WS управляющий канал.
15. Bridge находит локальную запись через mapping и передаёт команду нужному драйверу.
16. Драйвер выполняет протокольную операцию; Bridge отдельно сообщает принятие команды и итоговый результат.
17. Backend обновляет состояние и публикует событие.
18. Лампочка отключается: Backend сохраняет запись и последнее состояние, availability становится offline.
19. Лампочка возвращается: Bridge распознаёт прежнюю identity, использует прежний mapping, Backend обновляет availability=online без повторного выбора и без создания дубля.

Для первого сквозного теста допустим симулятор драйвера с управляемым pairing candidate. После проверки контрактов он заменяется реальным драйвером без изменения публичного UI API и доменной модели Backend.

## 15. Этапы реализации

1. Зафиксировать общий Device Contracts Go module: Device Type, Capability, Entity, command schemas, constraints, UI metadata и contract tests.
2. Зафиксировать Bridge ↔ Backend WebSocket actions и JSON Schema v1, включая pairing candidate, user selection, registration claim/result, command accepted/result, state и availability.
3. Реализовать Backend Physical Device Registry, identity mapping и pairing/registration service с отдельными SQLite-таблицами.
4. Реализовать Bridge Device Registry на SQLite и persistent mapping.
5. Реализовать Bridge service WS identity, отдельную privileged registration action и reconcile.
6. Реализовать Backend supervisor, Bridge health endpoint, stdin EOF shutdown, reconnect и readiness.
7. Реализовать Bridge discovery/pairing runtime и тестовый драйвер лампочки.
8. Реализовать автоматическую регистрацию после пользовательского выбора и восстановление ранее сопряжённых устройств.
9. Реализовать командную проверку Backend, Bridge Router и раздельные статусы accepted/result.
10. Реализовать передачу state/telemetry и публикацию UI events.
11. Подключить UI к Backend candidate list, pairing selection, device snapshot и event stream.
12. Провести интеграционный тест полного сценария лампочки, включая offline/online и reconnect.
13. После этого добавлять реальные протоколы и драйверы.

Каждый этап должен иметь unit, contract и integration tests. Contract tests Backend ↔ Bridge должны проверять несовместимую версию, некорректные сообщения, потерю WS, повторную service registration, истёкший candidate, повторное сопряжение известной identity, конфликт identity, неизвестную capability, устаревшую revision, недоступное устройство и ошибку исполнения команды.

## 16. Оставшиеся решения и границы спецификаций

Основная архитектура и пользовательская политика сопряжения согласованы. Следующие детали требуют отдельной фиксации в спецификациях до реализации соответствующих частей:

1. **Общий Device Contracts repository/module path.** Рекомендуем отдельный репозиторий `DaniilGavrin/HomeCloudDeviceContracts`, чтобы Backend и Bridge зависели от нейтрального общего модуля. Точный Go module path и имя репозитория нужно утвердить до создания.
2. **Неизвестный Device Type.** Рекомендуем сохранять обнаруженное устройство в ограниченном состоянии без исполняемых capabilities, а не отвергать весь факт обнаружения.
3. **Неизвестная Capability.** Рекомендуем отклонять неизвестную capability отдельно, сохраняя возможность работы с остальными подтверждёнными capabilities. Неизвестная capability никогда не становится исполняемой автоматически.
4. **Нестабильная identity.** Рекомендуем не выполнять автоматическое объединение; при отсутствии надёжной identity требуется явное сопоставление пользователем.
5. **Candidate TTL и discovery policy.** Время жизни candidate, поведение сканирования и ограничения параллельных pairing sessions фиксируются в Bridge Protocol / Driver API с учётом возможностей каждого протокола.
6. **Pairing credentials.** UI flow для PIN/QR/секретов определяется конкретным протоколом. Секреты не должны передаваться в логах или храниться в открытом виде.
7. **Командные timeout и неопределённый результат.** Принятие команды и итоговое исполнение — разные статусы. При потере соединения нельзя автоматически повторять неидемпотентную команду; поведение при неизвестном результате и timeout должно быть определено в Bridge Protocol.
8. **Точные wire contracts.** Имена actions, JSON Schema, error codes, correlation/idempotency и reconnect reconciliation фиксируются в `BRIDGE_PROTOCOL_V1.md`.
9. **Go driver API.** Интерфейсы, concurrency, lifecycle, cancellation, timeout и error mapping фиксируются в `DRIVER_API_V1.md`.

### Уже согласованные решения

- Новое физическое устройство обнаруживается только после физического перевода в режим сопряжения; пользователь выбирает candidate в UI, дальнейшая регистрация автоматическая.
- Повторное обнаружение надёжно известного сопряжённого устройства не требует повторного выбора.
- Backend назначает постоянный HomeCloud `device_id`; Bridge сохраняет локальный mapping.
- `hc_devices` остаётся реестром WS-клиентов; системный Bridge peer может присутствовать там, физические устройства — нет.
- Backend и Bridge используют общий версионируемый Go-пакет Device Contracts; драйверы остаются внутри Bridge.
- Backend и Bridge имеют отдельные SQLite-реестры физических устройств.
- Управляющий канал использует существующий Backend WebSocket JSON v1 на loopback; отдельный Unix Socket / Named Pipe не вводится.
- Backend запускает Bridge как supervised child process; stdin EOF инициирует graceful shutdown; health endpoint не заменяет WS registration/readiness.
- Команды имеют отдельные этапы принятия и итогового результата; offline-команды не ставятся в отложенную очередь.

## 17. Критерии готовности архитектуры v1

Архитектура считается согласованной, когда определены:

- границы ответственности Backend, Bridge, драйвера и UI;
- отдельные модели Backend Physical Device Registry и Bridge Device Registry;
- отдельная роль существующего `hc_devices` как реестра WS-клиентов;
- стабильная identity model и правила сопоставления повторно обнаруженных устройств;
- полуавтоматический pairing flow: физический pairing mode → discovery candidate → выбор пользователя → protocol pairing → автоматическая регистрация;
- состояния candidate, pairing, registration, paired и offline;
- модель Device Type / Capability / Entity / State и общий версионируемый Device Contracts пакет;
- формат декларации capabilities, версионирование и правила проверки Backend/Bridge;
- разделение статических контрактов и динамических данных экземпляров в SQLite;
- правила регистрации, обновления, offline/online и конфликтов идентичности;
- управляющий WebSocket JSON v1, service identity, privileged registration, heartbeat, health и graceful shutdown;
- формат команды, маршрутизация, accepted/result, timeout и ошибки;
- формат телеметрии и событий;
- модель доступных UI действий с учётом capabilities и permissions;
- правила совместимости версий и восстановления после сбоев;
- сквозной тест лампочки, включая первичное сопряжение, offline/online и повторное обнаружение.

**Главное правило:** Backend владеет постоянной HomeCloud-идентичностью и решает, что устройство может делать и кому разрешено это делать. Bridge знает, какое физическое устройство соответствует этой записи и как с ним взаимодействовать. UI знает только модель, которую предоставляет Backend.
